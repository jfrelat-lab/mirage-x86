## Performance

| Item | Effort |
|---|---|
| Compilation of cold blocks: about a fifth of a Windows 98 boot | M |
| Dispatch between blocks: ✅ under paging a block goes on through forward branches (side exits, skips), loops and followed calls, so Dhrystone runs some 30 instructions a dispatch where it ran five (docs/RECOMPILER.md); to do: the same without paging, where the DOS golden runs are timed to the block, and the second tier, which needs an instruction budget before it can be switched back on | 🔶 L |
| Byte-granular tracking of compiled code for the write barrier | M |
| Lazy flags, inline caches for indirect calls, registers as locals, a worker thread, an intermediate representation | L each |
| **Static recompilation, x86 to C, compiled by PRISM** (as the N64 and Xbox 360 recompilation projects do it): a program's functions, found by MIRAGE as it runs it (the blocks the recompiler translated, their calls and jump tables, recorded with a hash of their bytes), written as C over the machine's state (registers, flags, x87, memory MIRAGE's own), compiled by PRISM to JavaScript and loaded back: a function whose bytes still match runs whole, its branches inside one JavaScript function, its calls direct; anything not found yet stays with the dynamic recompiler, and the API calls go to MIRAGE's DOS and Win32 HLE as now. What it buys: the cost of dispatching a block (40% of the host's time under HotSpot's code, Flash's 9 M blocks a second) is gone, and the C is readable. First targets: 32-bit flat code with no packer or self-modifying code -- a DOS/4GW demo, WinQuake (PRISM compiles Quake's own source: the upper bound to compare with), then HotSpot; 16-bit DOS code (segments, far calls) later; packed intros only from a memory image once unpacked. Steps: (1) the block graph exported by function; (2) the C emitter, reusing the recompiler's semantics; (3) PRISM compiling it, its ABI the machine's state; (4) the loader and the guards; (5) timed against the dynamic recompiler in guest instructions. A whole-function tier inside the dynamic recompiler (one JavaScript function a guest function) gets the same dispatch gain with no C, and may come first. 🔶 **Started with 16-bit DOS intros (tools/recomp):** 19 of them translate, build with PRISM and clang, and are pixel-identical to MIRAGE (A000 and the DAC) at every frame, compared at the exact guest instruction count -- the oracle is MIRAGE run one instruction a block (MIRAGE_MAXOPS=1), and 3DAh's beam and the PIT's count are computed from that count in the C as MIRAGE computes them: tube, lattice, kaneda, puls, plasma13, xormunch (the bench set but memories), above, chaosequ, dirojed, endless, intoanew, intro256, mirrors, paralaxa, rv256, upup, warp, worm, 256bytef. PRISM against the dynamic recompiler, ms a frame: kaneda 2.9 vs 52.8 (18x), above 1.6 vs 30.8 (20x), puls 23.6 vs 287 (12x), chaosequ 26.5 vs 262 (10x), mirrors 13.7 vs 122 (9x), tube 3.0 vs 14.8 (4.9x), lattice 44.9 vs 65 (1.4x, x87-bound: native 28); a vsync-locked intro gains only its poll loop. The translator inlines near calls (a context per return address, the RET checked), follows DF and the x87 top statically (an edge renames the registers where two paths disagree), guards the code it translated at every frame point (a rewritten immediate becomes a memory read: lattice keeps its clock in one), models a 66h subset on upper-half locals, emits every intro as structured loops, and translates a packed or self-relocating program from a snapshot of MIRAGE's machine before its first frame point. Refused, by name: interrupt handlers (memories, animate, freality, omniscent, qblove, paleozoa, HELIUM: no interrupt reaches the C, and the oracle runs without its timer), text through the BIOS in mode 13h (256b, abstract, intro), protected mode (oktaeder, mesha), Mode X/planar (starport), SSE4 (crevenge), calls through a register (soullost), 67h (Heaven), HLT (revitro), undefined flags read (symetrie, difze, nibble). Walls: PRISM emits fmod as a runtime call (6.8x a bare remainder) and does not inline a static function into another (1.6x) -- tools/recomp/walls; MIRAGE's cycle count moves a block at a time, so what 3DAh and the PIT answer depends on where its blocks end, and a word OUT to 3C8h drops AH. Next: interrupts delivered at block boundaries with the oracle told where, indirect calls from MIRAGE's observed targets, the function model with MIRAGE's state as the ABI and the dynamic recompiler as fallback, then 32-bit flat code | XL |

Rule for all of them: a change that speeds up the paged systems must not slow the DOS player
(see [CONTRIBUTING.md](../CONTRIBUTING.md)).

The page chooses by parameter (`?net=ws://…`, `?net=local`) and falls back to mode 3 when there is no server | — |
| **Mode 1, server + browser**: `oasis serve` relays — Node opens real TCP/UDP sockets (`net`, `dgram`) and resolves names (`dns.lookup`), forwards ports into the guest, and is a hub for a LAN between tabs and machines. First user: AF_INET for MIRAGE-LINUX — wget, lynx, apt, Quake without `-noudp`, X clients over TCP | M |
| **Mode 3, browser only**: no raw sockets — a LAN between tabs of one browser over `BroadcastChannel` (DOOM in IPX, Quake in UDP, a Windows 95 network neighbourhood), the guest's HTTP turned into `fetch()` (CORS permitting), names by DNS-over-HTTPS; between machines WebRTC, with signalling by hand (a code to copy) or by a relay. Loopback always works | M |
| **Mode 2, external relay + browser**: a static page (GitHub Pages) and the URL of a relay — the network's relay taken out as `tools/relay.mjs`, deployable anywhere. Opt-in and said plainly: the traffic goes through a third party | S |
| **The NE2000 on v86's relays**: if the NE2000 speaks their protocol (raw Ethernet frames over WebSocket), the public relays v86 uses serve full systems (Windows 9x, Linux kernels) with no NAT of our own; else a user-mode NAT (QEMU's slirp) in Node | L |

## OASIS — images for every world of the period PC

A container format and runner on MIRAGE, the way Docker is one on Linux: an **image** is a manifest
(the world — DOS, Linux user space, Win16, a bootable PC — the machine profile, the entry point) and
file layers fetched on demand; `oasis run <image> [cmd]` runs it in a terminal, a native window or
the browser. What Docker does not: no daemon and nothing to install, the same x86 on every host
(phones included), a VGA screen and a Sound Blaster, period binaries (DOS, DPMI, a.out, Win16),
runs reproducible to the cycle, and a commit that saves the whole machine — CPU included — so a URL
resumes a program at the instant it was taken. The name: what a mirage promises, an oasis is.
